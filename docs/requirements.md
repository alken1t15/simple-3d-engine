# Требования и границы 3D-графического движка

**Версия:** рабочая базовая версия плана, 27.09.2026. P0 ниже — выбранный для проекта объем. Если команда позднее уточнит границы, изменения вносятся в этот документ с причиной.

Полный план разработки и риски описаны в [плане](../project_plan.md).

## 1. Рабочие границы

Проект — **3D-графический движок** с простыми примитивами, полигонами, текстурами, сценой из множества моделей и внешним API. Нужны демонстрационные сценарии, автоматические проверки там, где они применимы, и ручной smoke-check для графики. Игровая логика, физика и коллизии исключаются из базового объема.

Стек **C#** выбран для проекта. Конкретные .NET, OpenGL/OpenTK и форматы файлов — решения команды. OBJ-импорт, освещение, иерархия объектов, 1920×1080, редактор, презентация и строгий UML не входят в выбранный P0.

## 4. Сценарий A: текстурированный куб и камера

**Пользовательская цель:** приложение без знаний OpenGL показывает вращающийся текстурированный куб рядом с плоскостью и может изменить положение камеры.

| Шаг | Вызывающая программа делает | Движок должен обеспечить | Проверяет |
|---|---|---|---|
| A1 | Создает `Engine` и окно | Графический контекст, понятная ошибка при неудаче | P0-01/05 |
| A2 | Создает `Scene`, `Camera`, куб и плоскость | Данные mesh/камеры не требуют прямых GPU-вызовов | P0-02/03/04 |
| A3 | Загружает контрольную текстуру и назначает материал кубу | UV и корректное владение текстурой | P0-06/08 |
| A4 | Добавляет два объекта, задает разные transform | Независимое размещение объектов | P0-02/04 |
| A5 | Запускает рендер; меняет вращение куба и положение камеры | Обновленный кадр, перспектива, depth test | P0-04/05 |
| A6 | Закрывает окно штатным способом | Освобождение GPU-ресурсов без падения | P0-08 |

**Путь API:** `Engine.Create(options)` → `PrimitiveFactory.CreateCube/CreatePlane` → `Engine.LoadTexture` → `Scene.Add` → `Engine.Run(scene, camera, onUpdate)` → `Dispose`. `Engine.Run` владеет циклом окна, callback приложения меняет объекты сцены. Это решение плана, техническую осуществимость которого проверит spike. У приложения нет обязанности вызывать OpenGL, вручную создавать шейдер или GPU-буфер.

**Проверка архитектуры:** `Demo → публичный Engine/Scene/Camera → Core (данные) → OpenGL Renderer → окно`. Зависимость `Core → OpenGL` не нужна. GPU-ресурсами владеет `Engine`; сцена обновляется в callback приложения. В spike проверить жизненный цикл OpenTK, загрузку изображения и передачу матриц; точные сигнатуры окончательно зафиксировать в задаче 1.3.

## 5. Сценарий B: множество объектов и FPS

**Пользовательская цель:** приложение показывает около тысячи простых экземпляров геометрии и получает воспроизводимый результат замера.

| Шаг | Вызывающая программа делает | Движок должен обеспечить | Проверяет |
|---|---|---|---|
| B1 | Создает один mesh куба и при необходимости одну текстуру | Повторное использование ресурсов | P0-02/03/06 |
| B2 | Создает около 1000 `SceneObject` с разными transform и добавляет их в одну сцену | Хранение множества экземпляров; отсутствие 1000 копий mesh | P0-02/04/07 |
| B3 | Выставляет камеру, разрешение окна и режим VSync | Воспроизводимые условия показа | P0-04/07 |
| B4 | Прогревает и измеряет фиксированный интервал; фиксирует FPS и время кадра | Рендер без длительных существенных просадок и без роста памяти | P0-07/08 |
| B5 | Закрывает приложение и повторяет запуск | Освобождение ресурсов и повторяемость | P0-08 |

**Путь API:** создать один `sharedMesh` → добавить около 1000 объектов с разными transform → запустить `Engine.Run(scene,camera,onUpdate)` → завершить через `RequestClose` → использовать `RenderedFrames` и внешний `Stopwatch` → сохранить протокол. Публичная система профилирования не нужна. Рендерер кеширует GPU-представление общего mesh внутри `Engine`; это не требует универсальной системы кэша в публичном API.

**Внутренний профиль замера:** целевой стенд (раздел 8), одинаковое разрешение и число простых кубов, указать VSync, дать сцене прогреться, затем мерить не меньше минуты. Записать средний FPS и длительность просадок. Характеристики стенда — в разделе 8, фактические версии ПО и драйвера — в [описании стенда spike](spikes.md#стенд); точное разрешение записать при первом замере.

## 6. Итог проверки двух сценариев

| Вопрос | Вывод |
|---|---|
| Можно ли выполнить оба сценария только через предложенные модули? | **Да, на уровне архитектуры:** `Core` хранит сцену/данные, `OpenGL` создает окно и рендерит, `Demo` вызывает публичный путь. |
