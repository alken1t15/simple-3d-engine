# Процесс разработки, проверки и интеграции

**Статус:** план командной работы и базовое оформление репозитория. Репозиторий GitHub подготовлен для документации; документационный CI добавлен. Build/test CI добавлен для минимального Engine3D.sln; функциональных тестов пока нет. [Распределение зон](team.md) · [План задач](../project_plan.md).

## 1. Репозиторий и короткий цикл задачи

**Рабочий выбор:** один Git-репозиторий на GitHub для кода, документов и CI. Если у команды уже есть GitLab, тот же процесс переносится туда без изменения архитектуры. Самостоятельно поднимать сервер GitLab ради трехнедельного учебного проекта не планируется.

```text
Карточка задачи с критерием готовности
  → короткая ветка от актуального main
  → локальная сборка/нужные тесты
  → небольшой PR со ссылкой на задачу
  → автоматические проверки и ревью по правилам раздела 3
  → исправления автора
  → merge интегратором
  → при необходимости визуальный smoke на целевом ноутбуке
```

Для веток использовать понятные имена вроде `feature/mesh-data`, `feature/render-frame`, `docs/api-contract`. Коммиты должны описывать результат, а не «fix»/«update». Длинные ветки регулярно обновлять от `main`, чтобы интеграция не происходила в последний день.

## 2. Карточка задачи

Минимальные поля одной карточки:

| Поле | Пример для задачи 2.1 |
|---|---|
| ID и цель | `2.1 / Core`: сцена и геометрия для первого кадра |
| Ответственный/проверяющий | Фактические участники из [team.md](team.md) |
| Входные контракты | `Vertex`, `MeshData`, оси/UV, выбранные после spike 1.2 и задачи 1.3 |
| Результат | `Core` собирается; куб/плоскость и камера доступны через API |
| Проверка | Тесты индексов/матриц и `dotnet build` проходят |
| Зависимости | 1.3; ссылаться на блокирующую карточку |
| Не входит | Импорт OBJ, освещение, иерархия сцены |

Карточка достаточно мала, если ее можно проверить одним PR и сформулировать в одном-двух предложениях. Если PR смешивает API, рендер, тесты, ассеты и документацию разных функций, разделить его на независимые шаги.

## 3. Pull request и code review

В описании PR указывать: что изменилось; какую задачу закрывает; как проверено; скриншот/короткое видео для видимой графики при необходимости; какие ограничения остались. Шаблон:

```text
Задача: <ID и ссылка>
Результат: <наблюдаемое изменение>
Проверка: <команды тестов и/или ручной сценарий>
Риски/ограничения: <только реальные для этого PR>
```

**Правило принятия:** PR остальных участников должен получить `Approve` от двух разных человеческих reviewers, не являющихся автором; CI зеленый для всех PR; Алексей Зарубин (`alken1t15`) как Team Lead принимает PR и решение о merge. Codex может помогать с подготовкой и анализом, но не считается человеческим reviewer. Для собственных PR Team Lead действует подтвержденное исключение: чужие `Approve` не требуются, он может выполнить merge самостоятельно после успешных проверок. Для матриц, владения ресурсами и публичного API reviewers должны проверять затронутые контракты `Core` и рендера/клиентского сценария.

На ревью проверять прежде всего соответствие выбранному P0 и контракту, ошибки владения ресурсами, воспроизводимость тестов, случайные прямые OpenGL-вызовы в демо и права на добавленные ассеты. Форматирование не должно занимать основную часть обсуждения; базовые правила хранить в `.editorconfig`.

`main` должен оставаться собираемым. Если настройки хостинга позволяют, запретить прямые push и требовать успешные проверки и ревью перед merge.

## 4. Минимальный CI

Workflow [build.yml](../.github/workflows/build.yml) на `push` и `pull_request` устанавливает SDK из `global.json` и выполняет:

```sh
dotnet restore Engine3D.sln
dotnet build Engine3D.sln --configuration Release --no-restore
dotnet test Engine3D.sln --configuration Release --no-build
```

Версии тестовых пакетов зафиксированы в `Engine3D.Tests.csproj`. Пока функциональных тестов нет, тестовый шаг проверяет возможность запуска инфраструктуры и сообщает об отсутствии тестов; это не проверка поведения движка. Тесты Core добавляются вместе с реализацией.

Workflow [documentation.yml](../.github/workflows/documentation.yml) отдельно проверяет комплектность документов и отсутствие локальных путей. При появлении конфигурации стиля добавить проверку форматирования/анализаторов, если она не дает ложных блокировок.

Отдельные GPU-тесты и замер FPS **не считать пройденными CI**, если runner не имеет контролируемой видеокарты/экрана. Их проводят по записанному smoke-сценарию на целевом ноутбуке. CI сообщает о сборке и числовой логике, ручная проверка — о видимой картинке и поведении графического контекста.

## 5. Тестовые ворота по этапам

| Этап | Минимум перед merge/переходом |
|---|---|
| Контракты 1.3 | Сценарии A–D [API](api.md) выполнимы без внутренних классов; разработчики `Core` и рендера используют одни соглашения о данных. |
| Core 2.1 | Сборка и тесты индексов, примитивов, transform/камеры. |
| Первый рендер 2.2 | Визуально правильные цветной куб, камера, depth и закрытие окна; CI не заменяет эту проверку. |
| MVP 2.3 | Контрольная текстура не перевернута; прежняя цветная сцена работает; повторный запуск успешен. |
| Нагрузка 3.1 | Протокол с конфигурацией стенда, числом объектов/треугольников, VSync, временем и FPS. |
| Сдача 4.3 | Чистый клон собирается по README; тесты и smoke проходят; лицензии/вклад документированы. |

Если тест сломан существовавшим дефектом, PR не маскирует его пропуском без объяснения. Завести отдельную задачу и указать, почему текущий PR не может его исправить; для критического пути исправить до merge.

## 6. Сторонние ассеты и лицензии

Для каждого стороннего пакета, модели, текстуры и шейдера записывать название, источник, автора, лицензию и способ использования в `THIRD_PARTY.md` или аналогичной таблице. Не копировать игровые модели/текстуры с неизвестными правами. Контрольную PNG для MVP лучше сделать собственной: это одновременно дает надежный тест UV и убирает лицензионную неопределенность. Лицензия самого репозитория — отдельное решение; не считать MIT автоматически совместимой с каждым чужим ассетом.

## 7. Учет решений и изменений плана

До написания параллельных модулей зафиксировать короткую запись о контракте 1.3: форматы вершин/пикселей, конвенции матриц/UV, `Engine.Run`, владение GPU и ошибки. Если spike покажет, что выбранный контракт неудобен, изменить [архитектуру](architecture.md), [API](api.md) и связанные карточки **одним согласованным изменением**.

P1-функцию начинать только при работающем MVP и понятной оценке оставшегося времени. Перенос функциональности между P0/P1/P2 записывать в [requirements.md](requirements.md) с причиной, чтобы по истории проекта было видно, что именно команда обещала показать.
