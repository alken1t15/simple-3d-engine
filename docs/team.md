# Распределение работы команды

**Статус:** рабочая схема для заполнения именами участников. В лекции говорится о командах примерно по 9–10 человек, но фактический состав этой команды не передан. Имена, доступность и права в репозитории нельзя достоверно назначить заранее. Источник организационных ожиданий: лекция, с. 3–5, 8:49–16:52 и с. 8, 37:11–40:38; см. [описание источников](sources.md). Технические задачи: [основной план](../project_plan.md), [псевдокод](implementation_outline.md).

## 1. Принцип распределения

Каждая задача имеет **одного ответственного за результат** и одного проверяющего; помощь других участников не размывает эту ответственность. Работа делится по границам `Core`, `OpenGL`, демо/замеров и проверки. Один человек может вести несколько направлений, если команда меньше предполагаемой. На критическом пути не оставлять задачу у участника, который недоступен в ближайшие дни.

Тимлид или интегратор следит за зависимостями и принимает решения при конфликте контрактов. Он не обязан писать большую часть кода. Автор PR не принимает собственный PR. Ревью кода делают люди; автоматическая проверка или локальная LLM — дополнение.

## 2. Зоны ответственности и передача результата

| Зона | Что делает | Какие задачи плана | Что передает другой зоне |
|---|---|---|---|
| Координация и интеграция | Следит за P0, зависимостями, короткими PR, решениями по API; принимает изменения после проверок | 0.2, 0.3, 1.3, 4.3 | Зафиксированные контракты и порядок интеграции |
| Сцена и геометрия | `Scene`, `SceneObject`, `Transform`, `Camera`, `MeshData`, примитивы и числовые тесты | 2.1, часть 4.1 | Неизменяемый формат вершин/индексов и матриц |
| Окно и рендер | OpenTK spike, контекст, базовый шейдер, depth, GPU-кэш, цикл кадра, закрытие | 1.2, 2.2 | Публичный `Engine` и диагностируемые ошибки |
| Текстуры и ассеты | Декодер изображения, UV, контрольная PNG, лицензии сторонних ресурсов | 2.3, часть 4.3 | `TextureData` и проверочный образец |
| Демо и нагрузка | Базовый показ, сцена с ~1000 объектами, протокол FPS | 2.3, 3.1, 4.2 | Воспроизводимые команды запуска и результат замера |
| Тесты, CI и документация | `dotnet test`, интеграционные проверки без GPU, smoke-чек-лист, сборка в CI, README | 0.3, 4.1, 4.3 | Видимый статус сборки и инструкция запуска |

**Первый интеграционный стык:** разработчик сцены и разработчик рендера вместе проверяют `Vertex`, `MeshData`, конвенцию матриц, UV и жизненный цикл `Engine`. До этого параллельно можно готовить тест-кейсы, README, контрольную текстуру и инфраструктуру репозитория; публичные типы не разрабатывать независимо в двух ветках.

## 4. Распределение по моменту проекта

| Момент | Что идет параллельно | Что является общим контрольным результатом |
|---|---|---|
| После плана | OpenTK spike; создание репозитория и CI; подготовка контрольной текстуры/тест-кейсов | Результат spike и уточненный контракт 1.3 |
| После 1.3 | `Core` и рендер по единому формату; демо готовит сценарии; тесты покрывают данные | Сквозной цветной кадр через API |
| После первого кадра | Текстура; визуальные проверки; README; нагрузочная сцена | MVP с текстурированным кубом |
| После MVP | Нагрузка/замеры; выбранный P1, если есть время; регрессия и документация | Готовый показ и протокол производительности |

Приоритет при конфликте ресурсов: **сначала задачи, от которых зависит работающий P0**, затем улучшения. Не запускать P1, если текстура, глубина, закрытие окна или базовые тесты P0 еще не работают.

## 5. Как учитывать вклад и отсутствие участника

- Каждую задачу вести в issue/карточке с ID из плана, ответственным, проверяющим, результатом и ссылкой на PR. Вклад виден по закрытым задачам и содержательным PR, а не только по числу коммитов.
- На коротком командном созвоне сообщать: что сделано, что блокирует, какой следующий интеграционный шаг. Формальная Scrum-структура здесь не нужна.
- Если задача на критическом пути не движется, интегратор переносит ее другому доступному участнику и фиксирует это в карточке. Помощь первоначальному владельцу допустима; задача не должна ждать молча.
- Для PR по API, матрицам, рендеру и ресурсам проверяющими должны быть люди из **разных** затронутых зон, насколько позволяет состав команды.

## 6. Права на принятие PR и проверку

**Рабочее правило:** автор выполняет локальные проверки и открывает PR; два других участника проводят содержательное ревью; CI должен быть зеленым; интегратор/тимлид принимает PR. Если интегратор — автор, merge выполняет другой участник с правами после тех же проверок. Преподаватель рекомендовал не меньше двух человеческих ревью для каждого PR (лекция, с. 8, 37:11–40:38); для этой команды правило принято как план процесса.

**Кто тестирует:** автор проверяет свою задачу; владелец тестов поддерживает автоматические проверки; демо/нагрузку воспроизводит человек, не писавший соответствующий модуль; интегратор отвечает за то, что компоненты вместе проходят smoke-проверку. Подробный процесс — в [development-process.md](development-process.md).
