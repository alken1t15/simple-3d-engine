# Распределение работы команды

**Статус:** зафиксированы состав, роли, доступность и рабочие правила команды из шести человек. Назначения задач сверяются с GitHub Project; reviewer-кандидаты указаны в соответствующих issues. Технические задачи: [основной план](../project_plan.md), [псевдокод](implementation_outline.md).

## 1. Принцип распределения

Каждая задача имеет одного ответственного за результат. Reviewer-кандидаты и назначения фиксируются в GitHub issues; на каждый PR требуются два независимых человеческих одобрения. Работа делится по границам `Core`, `OpenGL`, демо/замеров и проверки.

Team Lead координирует интеграцию и разрешает конфликты контрактов; это не означает, что он должен писать большую часть кода. Автор PR не принимает собственный PR. Ревью проводят люди.

## 5. Как учитывать вклад и изменения назначения

- Каждую задачу вести в issue/карточке с ID из плана, ответственным, проверяющим, результатом и ссылкой на PR. Вклад виден по закрытым задачам и содержательным PR, а не только по числу коммитов.
- На коротком командном созвоне сообщать: что сделано, что блокирует, какой следующий интеграционный шаг. Формальная Scrum-структура здесь не нужна.
- Изменение владельца фиксируется в GitHub issue и Project. Помощь другим участникам не меняет назначенного владельца без обновления карточки.
- Для PR по API, матрицам, рендеру и ресурсам проверяющими должны быть люди из **разных** затронутых зон, насколько позволяет состав команды.

## 6. Права на принятие PR и проверку

**Рабочее правило:** автор выполняет локальные проверки и открывает PR; PR должен получить `Approve` от двух разных человеческих reviewers, не являющихся автором; CI должен быть зеленым. Алексей Зарубин (`alken1t15`) как Team Lead принимает PR и решение о merge. Codex помогает готовить и разбирать изменения, но не является человеческим reviewer и не учитывается в двух одобрениях. Если Team Lead — автор PR, merge после тех же проверок выполняет другой участник команды с необходимыми правами.

**Кто тестирует:** автор проверяет свою задачу; владелец тестов поддерживает автоматические проверки; демо/нагрузку воспроизводит человек, не писавший соответствующий модуль; интегратор отвечает за то, что компоненты вместе проходят smoke-проверку. Подробный процесс — в [development-process.md](development-process.md).
