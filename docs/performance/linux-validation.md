## Условия

- CPU Intel Core i5-12450H, 8 ядер / 12 потоков; RAM 16 GB LPDDR4X, ОС видит 15.3 GiB
- GPU Intel UHD Graphics Alder Lake-P, renderer `Mesa Intel(R) Graphics (ADL GT2)`, OpenGL `4.6 (Core Profile) Mesa 25.2.8-0ubuntu0.24.04.1`, драйвер Mesa iris, драйвер ядра i915; не llvmpipe/Xvfb
- Linux Mint 22.2, ядро 6.17.0-20-generic, сессия X11, Cinnamon (Muffin)
- .NET SDK 10.0.112, runtime 10.0.12; OpenTK 4.9.4
- Встроенный экран eDP-1 1920×1200, 60 Гц, масштаб 1.0 (Xft.dpi 96), других дисплеев нет. Окно: запрошено и фактически 1280×720, framebuffer 1280×720; WM размер не корректировал
- Питание от сети, батарея 100 %, профиль `balanced`. Частоты CPU/GPU и температура во время замера не записывались
- Фон: VS Code с Claude Code без активности во время замера, прокси NekoBox; браузер закрыт, сервер сборки .NET остановлен перед замером
- VSync запрошен off; фактически частота не ограничена: FPS намного выше 60 Гц
- Нагрузка по умолчанию из [методики](../performance.md): 1000 кубов / 12000 треугольников, общие mesh/material/texture, ambient и directional свет, неподвижные камера, объекты и свет

### Просадки

Оператор в обоих прогонах не заметил рывков, зависаний окна, мерцания или артефактов; курсор мыши вне окна двигался плавно. Сцена неподвижна, поэтому глазом заметны только явные зависания, а не субсекундные колебания темпа.

В данных оба прогона показывают одинаковую форму: около 30–40 секунд ровного темпа, затем уровень ниже до конца замера.

| | Прогон 1 | Прогон 2 |
|---|---|---|
| Медиана окон до понижения | 1399 FPS (0–38 с) | 1479 FPS (0–32 с) |
| Медиана окон после | 1297 FPS (38–60 с) | 1347 FPS (32–60 с) |
| Понижение | 7.3 % | 9.0 % |

Отдельные пониженные окна:

- прогон 1: 44.014–45.014 с (1139.83 FPS) и 54.017–55.018 с (1206.83 FPS);
- прогон 2: 33.012–35.013 с (1183.43 и 1144.61 FPS), 44.016–45.016 с (1152.24 FPS), 55.022–56.023 с (1147.28 FPS).

Наибольший callback gap — 5.60 ms в первом окне прогона 1 и 5.99 ms в окне 33.012–34.013 с прогона 2. Ни один промежуток между опросами приложения не превышал 6 ms, это меньше периода обновления экрана 60 Гц (16.7 ms). Gap не является временем отдельного кадра или моментом показа на дисплее: он включает события ОС, рендер, swap и инструментирование.

Причина понижения не установлена. Оно повторилось в обоих прогонах в похожее время, но частоты CPU/GPU, температура и троттлинг не записывались.

### Память

Форма ряда в обоих прогонах одинаковая:

- Working set растёт почти линейно, около 0.14 MiB/с, примерно со 127.3 MiB до 134.1–134.3 MiB. После сборки мусора в окне 43–44 с (прогон 1) или 41–42 с (прогон 2) он стоит ровно до конца замера: 134.34 MiB и 134.07–134.09 MiB.
- Managed растёт пилой, около 0.11 MiB/с, примерно 80 байт на показанный кадр. Одна сборка мусора снижает её с 6.7 до 1.3 MiB, затем рост продолжается. Источник аллокаций не исследовался.

Длительного роста после сборки не видно. Но за 60 с наблюдается один цикл GC, поэтому отсутствие утечки на длительном интервале не доказано. GPU memory не измеряется, численного порога для ряда не задаём.

## Ограничения

- Анализ интервальный: нет покадровых GPU timestamps, p95/p99 и точной длительности отдельных зависаний.
- Визуальная оценка на неподвижной сцене выявляет только явные зависания.
- Частоты CPU/GPU, температура и троттлинг не записывались; причина понижения FPS во второй половине замера не установлена.
- Фоновые VS Code и прокси работали во время замера; их влияние не оценивалось.
- Память наблюдалась 60 с с одним циклом GC; длительная стабильность и GPU memory не проверены.
- Проверены только размер окна 1280×720 и нагрузка по умолчанию.
