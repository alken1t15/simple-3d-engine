## Условия

- CPU Apple M3, 16 GiB RAM; встроенный GPU Apple M3, 8 GPU-ядер
- macOS 27.0.1 build 26A434; .NET SDK 10.0.401, runtime 10.0.12; OpenTK 4.9.4
- Реальный контекст в отдельной проверке кэша: vendor Apple, renderer Apple M3, OpenGL `4.1 Metal - 91.7`; не llvmpipe/Xvfb
- Встроенный Retina-дисплей 2560×1664; питание от сети. Частоту экрана, фактическое ограничение композитора/VSync, профиль энергосбережения и фоновые приложения отдельно не контролировали
- Запрошен клиент 1280×720 и VSync off. Tiling WM изменил окно до замера; после последнего изменения выполнен новый полный прогрев. Фактический клиент **720×874**, framebuffer **1440×1748**, затем размеры не менялись
- Нагрузка из [методики](../performance.md): 1000 кубов / 12000 треугольников, общие mesh/material/texture, обязательный ambient+directional свет, неподвижная камера. JSON сцены не используется

### Просадки: что действительно измерено

Наиболее медленное окно: **12.017–13.018 с от начала замера**, длительность 1.000907 с, 432 кадра, 431.61 FPS / 2.317 ms в среднем. Другие пониженные интервалы: 18.021–19.021 с (477.80 FPS), 10.014–11.015 с (544.64 FPS), 1.003–2.004 с (546.69 FPS), 5.006–6.006 с (547.83 FPS). Это разнесённые во времени замедления интервалов, а не ровный темп на протяжении минуты.

Самый большой callback gap — **40.6912 ms** в окне 27.029–28.030 с; FPS этого окна 631.26, среднее 1.584 ms. Средний FPS поэтому не описывает максимальный промежуток между опросами. Длительность самих просадок внутри секундных окон не установлена; gap включает события ОС/рендер/swap и может включать несколько refresh-кадров. Нельзя назвать его точным временем одного кадра или доказательством видимого зависания. Субъективная плавность и причина замедлений не проверены.

### Память

Working set в начале **148.125 MiB**, в конце **140.797 MiB**, диапазон **121.688–148.172 MiB**. Ряд не постоянный: на второй секунде падение примерно до 123 MiB, далее в основном 123–124 MiB; к 26–27 с около 122 MiB; на 28-й секунде скачок до 138 MiB, затем около 139–141 MiB до конца. Уменьшение между крайними точками не скрывает этот промежуточный рост.

Managed-оценка растёт примерно с **1.712 до 4.376 MiB** за минуту без принудительного GC. Это не доказательство утечки и не подтверждение её отсутствия: измеритель хранит интервальные записи, есть прочие аллокации и поведение GC/ОС. Стабильность памяти финальной версии на целевом стенде **не установлена**, численного порога для этого ряда не задаём.

## GPU-кэш и регрессионные проверки

Отдельный `performance-cache-smoke` на той же фабрике сцены (окно 320×180, framebuffer 640×360, вне FPS-интервала) завершился с кодом 0:

```text
OpenGL: Apple; Apple M3; 4.1 Metal - 91.7
1000 lit cubes: GPU meshes=1, textures=1; framebuffer=(640, 360)
After Dispose: GPU meshes=0, textures=0
```

Это прямое наблюдение внутренних счётчиков тестом, не счёт CPU-ссылок. Полный CPU-прогон: 393 passed / 28 skipped / 0 failed; новые CPU-кейсы — 19 passed. Release build — 0 warnings/errors. Обычный MVP Demo с `--frames 3 --no-focus` штатно завершил три кадра; это smoke запуска, не замена ручной проверки #13 на Linux.

При отладке до этого были два invalid-запуска, выявивших коррекцию размера окна WM, и полный прогон предыдущей версии измерителя (667.62 FPS). Затем зафиксирован один callback-делегат на запуск, и выполнен приведённый выше полный прогон окончательного кода (662.32 FPS). Это разные рабочие версии с неконтролируемым фоном: сравнение не доказывает ускорения/замедления, лучший результат не выбирался. Для приёмки нужны повторяемые прогоны одной commit-версии на целевом Linux-ПК с заполненными условиями и визуальными наблюдениями.
