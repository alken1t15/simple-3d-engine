# Нагрузочный сценарий B (#14)

## Статус и границы

Режим `--performance` встроен в `Engine3D.Demo`, использует только публичный API Core/OpenGL и не добавляет проектов или пакетов. Это воспроизводимый инструмент измерения, **не подтверждение финальной приёмки**. Для закрытия #14 нужен полный протокол на выбранном Linux-ПК `VladimirKhmelev` после smoke #13. Успех CI/llvmpipe и результаты других машин не заменяют эту проверку.

[Протокол целевого прогона на Linux-ПК](performance/linux-validation.md) от 20.10.2026: smoke #13, проверка GPU-кэша и два нагрузочных прогона с исходными JSON и заполненными `report.md`. Решение о приёмке #14 принимает Team Lead.

Доступен [дополнительный протокол macOS](performance/macos-validation.md) с исходным JSON, измеренными просадками/трендом памяти и ограничениями. Он проверяет работоспособность инструмента, а не закрывает Linux-приёмку.

## Фиксированная нагрузка

| Параметр | Значение по умолчанию |
|---|---|
| Объекты | 1000 кубов размера 1, сетка 10×10×10, шаг 2, центры от (0,0,0) до (18,18,18) |
| Геометрия | 12 треугольников на куб, 12000 всего; одна ссылка `MeshData` |
| Материал | Одна ссылка `MaterialData`, `BaseColor=(1,0.8,0.6)`, одна `TextureData` из существующей `Assets/control.png` |
| Свет P0-10 | Ambient RGB=(0.25,0.25,0.25), directional RGB=(0.75,0.75,0.75), направление лучей=(-1,-1.5,-2) |
| Камера | (35,30,40) → (9,9,9), FOV=60°, near=0.1, far=200 |
| Движение | Камера, геометрия и свет неподвижны; culling/instancing не добавляются |
| Размер | 1280×720 клиентских единиц; фактический framebuffer в физических пикселях автоматически записывается отдельно |
| VSync | Запрошен off; драйвер/композитор могут всё равно ограничить частоту |
| Прогрев / замер | 10 с / не менее 60 с, отсчёт по `Stopwatch` |

Окно оставляйте видимым, не сворачивайте, не меняйте размер и не переносите на экран с другим масштабом. При первом показе WM может скорректировать размер: до начала замера каждое такое изменение запускает полный прогрев заново и фиксирует новые фактические размеры. Изменение клиента/framebuffer **после прогрева** прерывает запуск с `invalid`; недоступный (нулевой) framebuffer недопустим и во время прогрева. Поэтому на компьютере с tiling WM фактический размер может отличаться от запрошенного — оба записаны в JSON. Окклюзию другим окном, ограничения композитора, энергосбережение и термотроттлинг приложение надёжно не распознаёт — их записывает оператор. Сцена и текстура создаются/валидируются до прогрева; JSON не используется.

## Запуск

Из корня чистой рабочей копии с SDK из `global.json`:

```sh
dotnet restore Engine3D.sln
dotnet build Engine3D.sln -c Release --no-restore
dotnet test Engine3D.sln -c Release --no-build
dotnet run --project src/Engine3D.Demo -c Release --no-build -- --performance --help
dotnet run --project src/Engine3D.Demo -c Release --no-build -- --performance \
  --output artifacts/performance/run-01 \
  --hardware "CPU: Intel Core i5-12450H; RAM: 16 GB LPDDR4X; GPU: Intel UHD Alder Lake-P; остальные условия дописать по факту"
```

Описание выше — известная конфигурация целевого ПК из [требований](requirements.md#целевой-стенд), не автоматическое определение машины запуска. Укажите фактический драйвер/версию ОС/дисплей/питание. Не копируйте описание целевого ПК в отчёт другого компьютера.

Допустимы `--size 1280x720`, `--vsync on|off`, `--warmup 10`, `--duration 60` (можно увеличить, но нельзя сократить обязательные интервалы). Параметры не смешиваются с `--load`, `--frames` и другими режимами Demo. Каталог `--output` должен быть новым: старый протокол не перезаписывается. Без `--output` создаётся уникальный каталог с UTC timestamp под `artifacts/performance/`.

Завершение автоматическое через `RequestClose`. Код возврата 0 означает полный интервал, **а не прохождение целевой приёмки**; 2 — неполный/отменённый/invalid замер; 1 — ошибка запуска/рендера/записи. Закрытие окна раньше прогрева даёт `cancelled-before-measurement`, после прогрева до автоматического завершения — `incomplete`. При ошибке внутри `Run` приложение по возможности сохраняет invalid-протокол и сообщает исходную ошибку; при ошибке до `Run` полноценного протокола нет.

## Формулы и файлы результатов

На первом callback после минимум 10 секунд при неизменном размере запоминаются точные `StartSeconds` и `StartFrames = RenderedFrames`. Граница может быть чуть позднее 10 с. Время отсчитывается от начала последнего полного прогрева (если WM менял размер, предыдущий прогрев отбрасывается). После фактических 60 секунд от этой границы callback вызывает `RequestClose`; после возврата `Run` сохраняются `EndSeconds` и `EndFrames`. Длительность включает небольшое завершение `Run`, но не запись отчёта и не `Dispose`.

```text
MeasuredFrames = EndFrames - StartFrames
MeasuredSeconds = EndSeconds - StartSeconds
FPS = MeasuredFrames / MeasuredSeconds
MeanFrameMs = 1000 * MeasuredSeconds / MeasuredFrames
```

Кадры прогрева исключены. `onUpdate` не считается показанным кадром; `RenderedFrames` включает refresh без callback. При отсутствии кадров средний frame time не определён (`null`), при отсутствии измеренного времени также не определён FPS.

В новом каталоге после `Run`:

- `measurement.json`: параметры нагрузки/света/камеры, клиент/framebuffer, запрошенный VSync, ОС/runtime/архитектура, версия сборки, описание стенда, реальные границы/счётчики и все интервальные наблюдения
- `report.md`: читаемый протокол, начальная/конечная память и диапазон, пять самых медленных интервалов и явно незаполненные ручные наблюдения

Файлы под `artifacts/` исключены из Git. Версия сборки может содержать Git hash, но не описывает незакоммиченные изменения: перед целевым прогоном запишите `git rev-parse HEAD` и проверьте `git status --short`.

Около раза в секунду сохраняются реальные границы интервала, прирост показанных кадров, FPS/средний frame time, максимальный промежуток между опросами приложения, process working set и `GC.GetTotalMemory(false)`. Последний интервал может быть короче. Во время замера нет файловой записи, readback пикселей или принудительного GC; стоимость опроса размеров/памяти включена в результат.

**Ограничения просадок:** это интервальный анализ, не покадровые GPU timestamps и не физические моменты появления изображения на дисплее. Максимальный callback gap включает события ОС/рендер/swap/инструментирование; refresh может нарисовать несколько кадров между callbacks. Не выдавайте его за время самого медленного кадра. Субсекундная просадка локализуется лишь внутри интервала; p95/p99 и точная длительность отдельных зависаний не измеряются. Интервалы длиннее секунды честно остаются длиннее секунды, а не превращаются в фиктивные «1-секундные» данные.

**Ограничения памяти:** working set — резидентная память всего процесса, managed — приблизительная живая память .NET без принудительного GC; GPU memory не измеряется. Опишите весь временной ряд: плато, пилообразные колебания, длительный рост или спад. Разница двух крайних точек не доказывает утечку или её отсутствие; численного допустимого порога не вводим.

## Наблюдение GPU-кэша без профилировщика в публичном API

Отдельная проверка строит **ту же** `PerformanceScene`, показывает несколько кадров и наблюдает внутренние счётчики из тестовой сборки: перед первым кадром 0/0, после первого и до конца 1 GPU mesh / 1 GPU texture, после `Dispose` 0/0. Это подтверждение переиспользования именно этой сцены, не вывод из равенства CPU-ссылок. Выполняется отдельно от FPS-прогона; не добавляет GPU handles в Demo или readback в измеряемый интервал.

```sh
# Одинаковая команда на Linux и macOS, главный поток для Cocoa:
dotnet tests/Engine3D.Tests/bin/Release/net10.0/Engine3D.Tests.dll performance-cache-smoke
# Либо в составе графических тестов (на macOS тест создаёт отдельный процесс):
ENGINE3D_GRAPHICS_TESTS=1 dotnet test Engine3D.sln -c Release --no-build --filter FullyQualifiedName~PerformanceCacheTests
```

Тест использует окно 320×180, без замера скорости. Сохраните вывод рядом с протоколом. Обычный `dotnet test` проверяет CPU-сцену, границы времени/счётчиков, early close, ноль кадров, параметры, JSON результатов; ожидания 70 секунд и GPU для него не нужны.

## Протокол целевой приёмки — заполняет оператор

1. На Linux-ПК Владимира выполните [smoke #13](../tests/Engine3D.ManualTests/manual_smoke_testing.md), запишите результат и ограничения. Работающий MVP со светом — предварительное условие, не вывод из нагрузочного теста
2. Зафиксируйте дату/commit/чистоту Git, `dotnet --info`, CPU/RAM/GPU, ОС, драйвер и фактический renderer (`glxinfo -B` при наличии), OpenTK 4.9.4, окно/framebuffer/масштаб/частоту экрана, питание/профиль, фоновые процессы. Не используйте llvmpipe/Xvfb для финального FPS
3. Запустите `performance-cache-smoke`, сохраните его вывод, затем performance-сцену с новым `--output` и точным `--hardware`
4. Во время всего интервала наблюдайте плавность, не трогайте окно. После завершения дополните `report.md`: были ли просадки, примерно когда/на сколько/какого характера, как они соотносятся с интервальными данными; ограничения точности не удаляйте
5. По всем `Samples` в JSON опишите наблюдаемый тренд памяти без выдуманного порога. Заполните оставшиеся ручные поля отчёта, приложите исходный JSON и результаты кэша. Повторите запуск в отдельный каталог для проверки воспроизводимости, не выбирайте только лучший результат

30–60 FPS — ориентир Team Lead, не обязательная численная гарантия преподавателя. Сам факт `complete` не подтверждает отсутствие просадок, стабильность памяти или правильность целевого оборудования.
