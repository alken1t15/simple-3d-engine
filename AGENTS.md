## Контекст и источники

Simple 3D Engine — учебный 3D-графический движок на C#/.NET 10 с OpenGL через OpenTK. Различай реализованный код, эксперимент и контракт будущей функции. Текущую готовность определяй по коду, README и связанным issue/PR; не считай примеры в документации работающей реализацией.

Читай документы по необходимости, а не весь комплект перед каждой небольшой задачей:

- Начало работы и команды: [README.md](README.md), [CONTRIBUTING.md](CONTRIBUTING.md).
- Требования и приёмка: [docs/requirements.md](docs/requirements.md); этапы и границы задачи: [project_plan.md](project_plan.md).
- Границы модулей: [docs/architecture.md](docs/architecture.md); сигнатуры, инварианты и ошибки: [docs/api.md](docs/api.md).
- PR, проверки и merge: [docs/development-process.md](docs/development-process.md).
- Изменения эксперимента OpenTK, графический запуск, Linux/WSL: [docs/spikes.md](docs/spikes.md).
- Участники и направления: [docs/team.md](docs/team.md); настройка доски: [docs/github-project.md](docs/github-project.md).

Для реализации сверяй связанную задачу с требованиями и API. Простое освещение и JSON собственной сцены входят в обязательный объём; импорт внешних моделей не требуется, отдельная анимация и culling — дополнительные возможности. Не расширяй объём отдельной задачи до всех функций движка.

## Архитектурные границы

- `src/Engine3D.Core`: CPU-данные, сцена, камера, преобразования, геометрия, свет и сериализация по контракту. Только стандартная .NET; без окна, OpenTK и OpenGL.
- `src/Engine3D.OpenGL`: публичный `Engine`, окно/контекст, рендер, декодирование изображений и GPU-ресурсы; зависит от Core.
- `src/Engine3D.Demo`: клиент публичного API Core/OpenGL; прямые `GL.*` и внутренние GPU-handles в демо не добавлять.
- `tests/Engine3D.Tests`: MSTest, CPU-проверки без обязательного графического контекста.
- `spikes/`: отдельный технический эксперимент. Переноси проверенное решение с учётом контракта движка; не подключай spike как зависимость библиотек.

Сохраняй четыре базовых проекта и существующее направление зависимостей. Новые библиотеки, пакеты и слои вводи только в согласованном объёме с обоснованием.

Для затронутой математической или графической логики сверяй разделы 7–9 API:

- Правая система координат, Y вверх, UV (0,0) снизу слева; CCW при взгляде снаружи.
- В Core используются row-vector матрицы: `model = scale * rotation * translation`, `MVP = model * view * projection`. Коррекция глубины `[0,1]` → `[-1,1]` выполняется ровно один раз в OpenGL-слое; передача полей System.Numerics в GLSL — `transpose=false`.
- Не меняй соглашение матриц ради локального исправления картинки. Преобразование нормалей при неравномерном масштабе и допустимость отрицательного масштаба определены разделом 8 API.
- Сохраняй неизменяемость MeshData/TextureData, копирование входных данных и доступ через ReadOnlySpan; GPU-кэш и shared mesh используют идентичность объектов.
- Валидация, типы исключений, поток контекста, callbacks и освобождение ресурсов должны соответствовать API. Не ослабляй проверки, чтобы тест прошёл.

## Подготовка к первой работе

Если инструменты уже установлены, не переустанавливай их. Для сборки нужны [Git](https://git-scm.com/install/) и [.NET 10 SDK](https://dotnet.microsoft.com/en-us/download/dotnet/10.0) для ОС и архитектуры компьютера. Скачивай именно SDK: одного Runtime для сборки недостаточно. По [global.json](global.json) допустим SDK `10.0.112` или более новый стабильный `10.0.*` с учётом `rollForward: latestFeature`; preview и переход на другую major/minor-версию не разрешены. Проверь окружение:

```sh
git --version
dotnet --list-sdks
```

Если локальной копии ещё нет, клонируй репозиторий в выбранную рабочую папку и перейди в его корень:

```sh
git clone https://github.com/alken1t15/simple-3d-engine.git
cd simple-3d-engine
dotnet --version
```

Если репозиторий уже клонирован, работай в существующей копии и выполни Git-проверки из раздела ниже. Прочитай README и CONTRIBUTING, затем связанную задачу и только затронутые требования/контракты. Для запуска Codex с этими инструкциями открывай корень репозитория. GitHub CLI (`gh`) нужен только при использовании его для операций GitHub; сборка от него не зависит.

При первом `dotnet restore` нужен доступ к NuGet: зависимости скачиваются автоматически, вручную скачивать OpenTK и тестовые пакеты не нужно. Для графического запуска дополнительно нужны драйвер/контекст OpenGL и системные оконные библиотеки; для Linux/WSL используй инструкции и проверенный X11-обход в docs/spikes.md. Не применяй WSL-обход ко всем платформам.

## Сборка, запуск и проверки

Используй .NET SDK, разрешённый [global.json](global.json); не меняй target framework или политику SDK для обхода ошибки окружения. Команды ниже выполняются из корня репозитория.

Для первой сборки и проверки работоспособности окружения, а также после изменений C# и сборочной конфигурации:

```sh
dotnet restore Engine3D.sln
dotnet build Engine3D.sln --configuration Release --no-restore
dotnet test Engine3D.sln --configuration Release --no-build
```

После успешной сборки Demo запускается из корня:

```sh
dotnet run --project src/Engine3D.Demo --configuration Release --no-build
```

При изменении Demo повтори его запуск. Сверяй фактическое поведение с README и `src/Engine3D.Demo/Program.cs`: сообщение о готовности каркаса не означает появления графического окна или готовности движка.

Для отдельного графического эксперимента OpenTK после настройки системных зависимостей из docs/spikes.md:

```sh
dotnet run --project spikes/OpenTkSpike --configuration Release
```

Эта команда собирает и запускает эксперимент, а не `Engine3D.Demo`; в WSL для неё может потребоваться `XDG_SESSION_TYPE=x11` по инструкции spike. Не требуй графического окружения для CPU-тестов Core.

При изменении spike или его workflow выполни `dotnet test spikes/OpenTkSpike.Tests --configuration Release`. Графический smoke запускай по docs/spikes.md и [.github/workflows/spikes.yml](.github/workflows/spikes.yml): ему нужны оконная система и системные библиотеки. Xvfb/программный OpenGL проверяют поведение, а не FPS целевого GPU.

Для Markdown-only изменений проверь ссылки, наличие требуемых документов и правила [.github/workflows/documentation.yml](.github/workflows/documentation.yml). Не запускай сборку и GPU-тесты без связи с правкой. Для любых изменений проверь `git diff --check`; новый неотслеживаемый файл также проверь до commit.

Исправление дефекта подтверждай воспроизводящим тестом или проверкой. Для численной логики проверяй границы и обосновывай допуски; не подменяй проверку копией алгоритма. Запускай релевантные тесты; после их успеха повторяй или расширяй проверку только при новых изменениях, сбоях или нерешённых вопросах. Если проверка недоступна, укажи причину и фактически выполненные проверки; отсутствие запуска не означает успех.

## Стиль и материалы

Соблюдай [.editorconfig](.editorconfig): UTF-8, LF, четыре пробела в C#, два в Markdown/YAML. Сохраняй nullable-контекст и принятые имена `Engine3D.*`. Публичные методы и нетривиальные инварианты документируй в стиле существующего кода. Обновляй затронутые документы при согласованном изменении поведения или API.

Не публикуй ключи, токены, абсолютные пути рабочего компьютера и личные журналы Team Lead. Локальные инструкции пользователя применяй, если они предоставлены, но не копируй их внутренние данные в репозиторий. Для стороннего пакета или ассета укажи источник и лицензию в [THIRD_PARTY.md](THIRD_PARTY.md) в том же PR; лицензия проекта — [MIT](LICENSE).

## Git и GitHub

- Перед изменениями проверь ветку, `git status` и diff, обнови сведения через `git fetch --prune`. Не делай pull при незакоммиченных изменениях. Для чистой ветки допустим только `pull --ff-only`; не перезаписывай чужие изменения.
- Работай в отдельной ветке от актуального `main`. При ревью чужого PR проверяй точный HEAD в отдельной копии; код автора не исправляй без отдельного поручения.
- Перед commit и push покажи diff и результаты проверок, получи подтверждение пользователя. Уже данное подтверждение в рамках согласованного объёма действует; не спрашивай повторно. Добавляй в commit только файлы задачи. Не делай прямой push в main, force-push и разрушительные Git-операции без явного разрешения.
- После согласованных commit и push автоматически создай PR, проверив, что PR этой ветки ещё не открыт. Используй конкретный русский заголовок и описание по [.github/PULL_REQUEST_TEMPLATE.md](.github/PULL_REQUEST_TEMPLATE.md): задача, результат, проверки и реальные ограничения. Частичная работа по issue не даёт основания закрывать её.
- В PR автора `alken1t15` никого не назначай reviewer: ни пользователей, ни команды. Чужие Approve для собственных PR Team Lead не требуются; успешный CI сохраняется. Для PR остальных участников действуют два независимых человеческих Approve, автор исключён. AI-ревью не заменяет человеческие одобрения.
- Создание PR не разрешает merge. Не создавай новые issues и не меняй назначения, даты, labels или Project-поля без согласования.

При порученном ревью проверяй требования, контракт и реальные сценарии, а не только зелёный CI. Замечание должно содержать файл/место, причину, последствия и способ воспроизведения или проверки исправления. Публикуй только подтверждённые замечания в исходном PR при разрешении пользователя; отдельный PR для ревью и пустой комментарий не нужны. Approve публикуй только при разрешении пользователя и после завершённых проверок; привязывай результат к проверенному HEAD. При обновлении HEAD заново проверь затронутые изменения.

В итоговом сообщении укажи результат, выполненные проверки, существенные ограничения и состояние публикации. Не выдавай CPU-тесты, сборку или AI-ревью за проверку GPU, FPS и готовность MVP.
